- **Phase M part 1 (poster edit propagation) -- DONE and verified:** new `propagation.py` + a new `whatsapp.py:send_opportunity_update_notification()`, called from `poster_flow._confirm_and_send_opportunity()`'s edit branch. `poster_flow` now snapshots the opportunity row *before* the UPDATE (`_get_opportunity_by_id`) because Section 3D requires comparing old vs. new values to know what actually moved -- doing it after the write would make every edit look like it changed everything. The new module then (a) diffs the 8 comparable fields, (b) notifies every row still linked to the opportunity, and (c) re-syncs the parts of those rows that were *derived* from the poster's dates. Notifications: a deadline move produces the Section 3.1 mandatory explicit line (`Deadline moved to Sep 25, 2026.`) plus `Your reminders have been adjusted automatically.`; other edits get plain-language lines (`The description was updated.`, `The application link was updated.`, `Results date is now ...`); a title change needs no line because the new title is the message heading; and when only the title changed the message says "The opportunity details were updated." rather than falsely claiming reminders moved. It is never batched and never routed through the Phase L scheduler, per 3.1. Date sync (Section 3D): `deadline_heads_up_sent` is reset to false whenever the deadline moved, so the one-time 2-day heads-up re-arms against the new date; `scheduled_event_date` follows a changed `event_start_date`; and `next_reminder_at` on `under_review` rows is re-derived from a changed `result_date` (or falls back to +3 days if the poster removed it, per 8.4). **The sync only touches poster-*derived* values**: it overwrites `scheduled_event_date` / `next_reminder_at` solely when the row's current value still equals what the *old* poster value implied, so a date the user typed themselves (Phase K's `outcome_event_date` flow, or a custom reminder time) is never stomped -- the single riskiest thing about editing propagation, and it is covered by tests. Two deliberate spec calls, both documented in the module docstring: (i) the notification set is every linked row in `available`/`ongoing`/`under_review`/`scheduled`, not just 3.1's literal "available or ongoing" parenthetical, because that sentence predates `under_review`/`scheduled` existing and the matching example says "Everyone tracking this will be notified" -- a user whose accepted event date just moved is exactly who must not be missed; (ii) propagation runs in its own try/except after the edit is saved, so a propagation failure can never be reported to the poster as "saving failed" or leave them without a reply (the existing "All tracked users will be notified of the changes." message was previously false -- nothing actually notified anyone -- and is now true).
